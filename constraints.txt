# WARUM. Bis 02.09.2026 stand in jeder Requirements-Zeile nur eine Untergrenze.
# Damit installierte jeder Lauf die jeweils neueste Fassung — und drei
# Umgebungen liefen auseinander, ohne dass es irgendwo aufgefallen wäre.
# Gemessen an diesem Tag:
#
#     Prod   fastapi 0.137.2
#     Dev    fastapi 0.139.2
#     CI     was immer an dem Tag neu war
#
# Die CI prüfte also gegen etwas, das auf Prod nicht läuft, und ein Deploy
# konnte eine neue Hauptfassung mitbringen, ohne dass ein Mensch sie gesehen
# hätte. Ein Bruch daraus erscheint nicht im Diff eines PRs; er erscheint als
# 500er, Stunden später.
#
# WOHER DIE ZAHLEN. Aus `pip freeze` der PROD-Umgebung, nicht vom Notebook und
# nicht von dev: Das ist der Stand, der die Seite trägt. Dev zieht damit auf
# Prod zurück, statt Prod vorwärts zu reißen.
#
# WIE MAN AKTUALISIERT. Bewusst, in einem eigenen PR: Zeile ändern, CI läuft
# gegen die neue Fassung, danach fährt sie mit dem nächsten Deploy. Für alles
# auf einmal:
#
#     pip install -r requirements.txt -r requirements-dev.txt --upgrade
#     pip freeze --exclude-editable > constraints.txt   # Kopf wieder davor
#
# WAS DIESE DATEI NICHT TUT. Sie installiert nichts. Eine Zeile für ein Paket,
# das gar nicht angefordert wird, bleibt wirkungslos — deshalb stehen hier auch
# `fastembed`, `onnxruntime`, `pymupdf` und `yt-dlp`, die auf dem Server von
# Hand nachinstalliert sind und bewusst in keiner Requirements-Datei stehen.
# Sie sind damit wenigstens festgehalten.
#

# Begründung für seine offene Grenze steht in `ruff.toml`.
